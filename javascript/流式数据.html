前端获取流式数据的主流方案与实践 ​

在现代 Web 应用中，实时数据交互变得越来越重要。流式数据（Streaming Data）技术允许服务器持续地、分块地将数据发送到客户端，而不是等待所有数据准备好后一次性返回。这种模式对于实时聊天、股票行情、AI 大语言模型交互等场景至关重要。

为什么需要流式数据？ ​

  1. 实时性 (Real-time): 服务器可以随时将最新的数据推送给前端，实现低延迟的数据更新。
  2. 处理大型数据 (Large Payloads): 对于大文件或 AI 生成的长文本，可以边接收边处理，极大降低前端内存压力，并提供更快的首次响应。
  3. 节省资源 (Resource Saving): 相比于传统的轮询（Polling），流式技术通过保持长连接来避免大量不必要的 HTTP 请求，减少服务器和网络的负担。

本文将系统梳理并对比前端获取流式数据的主流技术，并深入探讨它们各自的适用场景。

方案一：Server-Sent Events (SSE) ​

SSE 是一种基于标准 HTTP 的、服务器到客户端的单向通信技术。它非常适合那些只需要从服务器接收更新的场景。

工作原理: 前端通过 EventSource API 发起一个 HTTP 请求。服务器保持该连接打开，并以 Content-Type: text/event-stream 的格式持续推送文本数据。

优点:

  • 简单易用: 前端 API EventSource 非常简洁。
  • 基于 HTTP: 无需特殊协议，能良好地穿透防火墙和代理。
  • 自动重连: 如果连接意外断开，浏览器会自动尝试重新连接。
  • 自定义事件: 可以发送不同类型的事件，便于前端分类处理。

缺点:

  • 单向通信: 只能从服务器到客户端。
  • 连接数限制: 浏览器对同源的 SSE 连接数量有限制（通常为 6 个）。
  • 只支持 UTF-8 文本: 不适合传输二进制数据。

代码示例 ​

前端 (JavaScript)

javascript
// 1. 创建 EventSource 实例
const sse = new EventSource('/api/stream-sse');

// 2. 监听默认的 "message" 事件
sse.onmessage = (event) => {
  const data = JSON.parse(event.data);
  console.log('收到默认消息:', data);
  // 更新 UI...
};

// 3. 监听自定义事件 "update"
sse.addEventListener('update', (event) => {
  const updateInfo = JSON.parse(event.data);
  console.log('收到 update 事件:', updateInfo);
});

// 4. 监听连接打开
sse.onopen = () => {
  console.log('SSE 连接已建立。');
};

// 5. 监听错误
sse.onerror = (error) => {
  console.error('SSE 发生错误:', error);
  if (sse.readyState === EventSource.CLOSED) {
    console.log('连接已关闭');
  }
};

后端 (Node.js/Express 示例)

js
// server.js
// server.js
app.get('/api/stream', (req, res) => {
    // 设置响应头
    res.setHeader('Content-Type', 'text/event-stream');
    res.setHeader('Cache-Control', 'no-cache');
    res.setHeader('Connection', 'keep-alive');
    res.flushHeaders(); // 发送头部

    let count = 0;
    const intervalId = setInterval(() => {
        count++;
        // 发送默认消息
        res.write(`data: ${JSON.stringify({ id: count, time: new Date() })}\n\n`);

        // 发送自定义事件
        if (count % 5 === 0) {
            res.write(`event: update\n`);
            res.write(`data: ${JSON.stringify({ message: `这是第 ${count} 次更新` })}\n\n`);
        }
    }, 1000);

    // 客户端关闭连接时，清除定时器
    req.on('close', () => {
        clearInterval(intervalId);
        res.end();
    });
});

方案二：WebSocket ​

WebSocket 提供了**全双工（Full-duplex）**的通信能力，即客户端和服务器可以随时互相发送数据。它是一种独立的协议 (ws:// 或 wss://)。

工作原理: 通过一个特殊的 HTTP 请求进行握手，握手成功后，连接会“升级”为 WebSocket 连接，后续数据传输不再遵循 HTTP 协议，开销极小。

优点:

  • 全双工通信: 客户端和服务器可以双向、实时地通信。
  • 低延迟: 数据传输开销小，延迟极低。
  • 支持二进制: 原生支持传输文本和二进制数据。
  • 无跨域问题: 协议本身设计就支持跨域。

缺点:

  • 协议不同: 可能需要服务器和网络代理进行额外配置。
  • 实现稍复杂: 需要手动处理连接的生命周期和重连逻辑。

代码示例 ​

前端 (JavaScript)

javascript
// 1. 创建 WebSocket 实例
const ws = new WebSocket('ws://localhost:8080/ws');

// 2. 监听连接建立
ws.onopen = () => {
  console.log('WebSocket 连接已打开。');
  ws.send('你好，服务器！');
};

// 3. 监听从服务器收到的消息
ws.onmessage = (event) => {
  console.log('收到服务器消息:', event.data);
};

// 4. 监听连接关闭
ws.onclose = (event) => {
  console.log('WebSocket 连接已关闭。', event.code, event.reason);
  // 在这里可以实现重连逻辑
};

// 5. 监听错误
ws.onerror = (error) => {
  console.error('WebSocket 发生错误:', error);
};

方案三：Fetch API + ReadableStream ​

这是近年来处理流式响应（尤其是 AI 大模型输出）最流行和标准的方式。它利用了 Fetch API 返回的 Response 对象中的 body 属性，这是一个 ReadableStream。

工作原理: 前端发起一个标准的 fetch 请求。如果服务器响应是流式的，前端就可以通过 response.body.getReader() 来逐个读取离散的数据块(chunk)。

优点:

  • 现代标准: W3C 标准，专为流式处理设计。
  • 控制力强: API 设计清晰，可以精确控制数据的读取、解码和处理。
  • 内存友好: 数据以离散块的形式处理，无需维护一个不断增长的完整响应字符串，内存效率高。
  • 与 Service Worker 配合良好: 可以在 Service Worker 中拦截和处理流。

缺点:

  • 实现相对复杂: 对比 SSE，需要手动处理流的读取、解码 (TextDecoder) 和数据拼接。
  • 无内置重连: 需要手动实现。

代码示例 ​

前端 (JavaScript)

javascript
async function fetchStream() {
  try {
    const response = await fetch('/api/llm-stream');

    if (!response.body) {
      throw new Error("当前浏览器不支持 ReadableStream");
    }

    const reader = response.body.getReader();
    const decoder = new TextDecoder('utf-8');
    
    while (true) {
      // 读取一个离散的数据块 { value: Uint8Array, done: boolean }
      const { value, done } = await reader.read();
      
      if (done) {
        console.log('流已结束。');
        break;
      }
      
      const chunk = decoder.decode(value, { stream: true });
      console.log('收到一个数据块:', chunk);
      // 在这里处理每个独立的数据块
    }
  } catch (error) {
    console.error('Fetch Stream 错误:', error);
  }
}

fetchStream();

补充：使用 Axios 处理流式数据 ​

Axios 是一个非常流行的 HTTP 请求库，但它在浏览器端处理流式响应的机制与 fetch 有本质不同。虽然 fetch 是处理流式响应的首选方案，但了解 Axios 的能力也同样重要。

工作原理：onDownloadProgress ​

Axios 基于 XMLHttpRequest (XHR)，它提供了 onDownloadProgress 回调。每次浏览器接收到新的数据片段时，这个回调就会被触发。通过 progressEvent.target.response (或 responseText)，我们可以访问到从请求开始到当前时刻接收到的所有数据。

这并非像 fetch 那样提供离散的数据块，而是提供一个不断增长的累积字符串。我们需要手动处理，从中提取出新增的部分。

代码示例 ​

javascript
import axios from 'axios';

let lastResponseLength = 0;

axios({
  method: 'get',
  url: '/api/llm-stream',
  // 注意：在浏览器中，responseType: 'stream' 无效
  onDownloadProgress: (progressEvent) => {
    // progressEvent.target 是 XMLHttpRequest 实例
    const xhr = progressEvent.target;
    const allDataReceivedSoFar = xhr.response; // 或 xhr.responseText

    // 通过比较长度，提取本次新增的数据
    const newData = allDataReceivedSoFar.substring(lastResponseLength);
    lastResponseLength = allDataReceivedSoFar.length;

    console.log('收到新增数据:', newData);
    // 在这里处理 newData，例如解析并更新 UI
  },
}).then(response => {
  console.log('请求完成，最终完整数据:', response.data);
}).catch(error => {
  console.error('Axios 请求出错:', error);
});

对比与局限性 ​

  1. 数据处理方式:

    • Axios: 提供累积的完整数据。开发者需要手动记录上一次的长度，并通过字符串截取 (substring) 来获取增量数据。
    • Fetch: 提供离散的数据块 (chunk)。API 更直观，处理逻辑更清晰。

  2. 性能和内存:

    • Axios: 随着数据接收，responseText 字符串会越来越大，频繁的字符串截取操作在处理非常大的数据流时，可能会带来性能和内存上的开销。
    • Fetch: ReadableStream 的设计就是为了高效处理流，每次只处理小块数据，内存占用更稳定。

  3. 标准与未来:

    • Fetch + ReadableStream 是 WHATWG 定义的现代 Web 标准，是未来流式处理的趋势。
    • 使用 onDownloadProgress 是一种基于旧 XMLHttpRequest API 的变通方法。

结论: 虽然技术上可以使用 Axios 的 onDownloadProgress 来实现流式数据的接收和处理，但这种方式相对繁琐且效率较低。对于需要处理流式响应的场景（如 AI 对话），强烈推荐使用 fetch API，因为它提供了更现代化、更高效、更符合语义的 ReadableStream 接口。

如何选择？ ​

  • 简单推送，用 SSE：如果只需要从服务器接收实时更新，且不需要客户端频繁发消息。
  • 复杂交互，用 WebSocket：如果需要客户端和服务器之间进行频繁、低延迟的双向通信。
  • 处理大响应体或 AI 流，首选 Fetch Stream：这是最现代、最高效、最标准的方案。
  • 项目中已深度使用 Axios：可以采用 onDownloadProgress 的方法作为一种兼容方案，但要清楚其局限性。
