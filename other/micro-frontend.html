Qiankun主子应用通信：解决多处监听事件只执行一次的问题 ​

在使用 qiankun + Vue 3 搭建微前端项目时，一个常见的通信需求是：主应用更新一个全局状态，子应用内的多个组件都需要监听到这个变化并做出响应。但很多开发者会遇到一个问题：

当页面上有多个组件同时监听同一个 qiankun 全局状态事件时，最终只有一个组件的监听回调被触发了。

本文将深入分析这个问题背后的原因，并提供几种解决方案，帮助你彻底搞定它。

问题复现 ​

假设主应用通过 qiankunActions 触发一个事件：

javascript
// 主应用中
qiankunActions.setGlobalState({
    refreshEvents: {
        'REFRESH_UPLOAD': {
            payload: { /* 一些数据 */ },
            timestamp: Date.now() // 确保每次对象引用都不同
        }
    }
});

在子应用的某个页面上，有两个组件 ComponentA 和 ComponentB 都需要监听 REFRESH_UPLOAD 事件。

javascript
// ComponentA.vue
import { onMounted } from 'vue';
import { actions } from '@/qiankun'; // 假设 actions 是从 props 传入的

onMounted(() => {
  actions.onGlobalStateChange(state => {
    if (state.refreshEvents?.REFRESH_UPLOAD) {
      console.log('组件A 监听到事件');
      // ...执行逻辑
    }
  });
});

// ComponentB.vue
import { onMounted } from 'vue';
import { actions } from '@/qiankun';

onMounted(() => {
  actions.onGlobalStateChange(state => {
    if (state.refreshEvents?.REFRESH_UPLOAD) {
      console.log('组件B 监听到事件');
      // ...执行逻辑
    }
  });
});

结果：通常只有后挂载的那个组件（比如 ComponentB）会打印日志，ComponentA 的监听似乎“失效”了。

根源分析 ​

这个问题的核心在于 qiankun 的 onGlobalStateChange API 的设计。

onGlobalStateChange(callback, fireImmediately) 方法是注册一个回调函数。当你多次调用它时，新的回调函数会覆盖掉旧的回调函数，而不是追加。

因此，在上面的例子中，ComponentB 在 onMounted 中调用的 actions.onGlobalStateChange 覆盖了 ComponentA 注册的回调。最终，qiankun 的事件监听器列表中只存在 ComponentB 的回调函数，自然也就只有它会执行。

方案一：应用内事件总线（Event Bus） - 官方推荐 ​

这是解决此类问题的最佳实践。思路是：只在子应用入口注册唯一一个全局监听器，当监听到状态变化后，通过子应用内部的事件总线将事件分发出去。

步骤 1: 安装事件总线库 ​

推荐使用轻量级的 mitt。

bash
npm install mitt
# or
yarn add mitt

步骤 2: 封装 Qiankun Actions 和事件总线 ​

在 src 目录下创建一个文件，如 src/qiankun/actions.js，用于统一管理。

javascript
// src/qiankun/actions.js
import mitt from 'mitt';

// 1. 创建一个应用内事件总线实例
export const emitter = mitt();

class QiankunActions {
  actions = {
    onGlobalStateChange: () => {},
    setGlobalState: () => {},
  };

  /**
   * 注册 qiankun actions，并在此处设置唯一的全局监听
   */
  setActions(actions) {
    this.actions = actions;
    // 2. 注册唯一监听器
    this.actions.onGlobalStateChange((state, prevState) => {
      console.log('[子应用] 全局状态变化:', state);

      // 检查我们关心的事件对象
      if (state.refreshEvents && state.refreshEvents !== prevState.refreshEvents) {
        // 3. 遍历所有事件，通过内部 emitter 分发
        for (const eventName in state.refreshEvents) {
          console.log(`[子应用] 分发内部事件: ${eventName}`);
          emitter.emit(eventName, state.refreshEvents[eventName].payload);
        }
      }
    });
  }

  /**
   * 封装 setGlobalState
   */
  setGlobalState(state) {
    this.actions.setGlobalState(state);
  }
}

const qiankunActions = new QiankunActions();
export default qiankunActions;

步骤 3: 在子应用入口 main.js 中初始化 ​

javascript
// src/main.js
import { createApp } from 'vue';
import App from './App.vue';
import qiankunActions from './qiankun/actions';

// ...

export async function mount(props) {
  console.log('[子应用] mount');
  // 在 mount 时进行初始化
  if (props.onGlobalStateChange) {
    qiankunActions.setActions(props);
  }
  render(props);
}

// ...

步骤 4: 在组件中使用 emitter 监听事件 ​

现在，任何组件都可以安全地、不冲突地监听事件。

vue
<!-- ComponentA.vue -->
<script setup>
import { onMounted, onUnmounted } from 'vue';
import { emitter } from '@/qiankun/actions';

const handleRefresh = (payload) => {
  console.log('组件A 接收到 REFRESH_UPLOAD 事件', payload);
  // ...业务逻辑
};

onMounted(() => {
  emitter.on('REFRESH_UPLOAD', handleRefresh);
});

onUnmounted(() => {
  // 务必在组件销毁时移除监听，防止内存泄漏
  emitter.off('REFRESH_UPLOAD', handleRefresh);
});
</script>

ComponentB 也采用完全相同的方式监听，两者都能成功接收到事件。

方案二：手动实现单例模式 - 深入理解原理 ​

事件总线库（mitt）的本质就是一个单例实例。我们也可以自己动手实现一个，这有助于加深理解。

核心思想 ​

创建一个全局唯一的 GlobalStateObserver 类，由它来负责：

  1. 唯一注册 onGlobalStateChange。
  2. 内部维护一个所有组件的回调函数列表。
  3. 监听到变化后，遍历并执行列表中的所有回调。

代码实现 ​

javascript
// src/qiankun/GlobalStateObserver.js
class GlobalStateObserver {
    static instance = null;
    listeners = new Map();

    constructor() {
        if (GlobalStateObserver.instance) {
            return GlobalStateObserver.instance;
        }
        GlobalStateObserver.instance = this;
    }

    static getInstance() {
        if (!GlobalStateObserver.instance) {
            GlobalStateObserver.instance = new GlobalStateObserver();
        }
        return GlobalStateObserver.instance;
    }

    init(qiankunActions) {
        qiankunActions.onGlobalStateChange((state, prevState) => {
            if (state.refreshEvents && state.refreshEvents !== prevState.refreshEvents) {
                for (const eventName in state.refreshEvents) {
                    this._dispatch(eventName, state.refreshEvents[eventName].payload);
                }
            }
        });
    }

    _dispatch(eventName, payload) {
        if (this.listeners.has(eventName)) {
            this.listeners.get(eventName).forEach(callback => callback(payload));
        }
    }

    on(eventName, callback) {
        if (!this.listeners.has(eventName)) {
            this.listeners.set(eventName, []);
        }
        this.listeners.get(eventName).push(callback);
    }

    off(eventName, callback) {
        if (this.listeners.has(eventName)) {
            const callbacks = this.listeners.get(eventName);
            const index = callbacks.indexOf(callback);
            if (index > -1) callbacks.splice(index, 1);
        }
    }
}

export default GlobalStateObserver.getInstance();

使用方式 ​

使用起来和事件总线几乎一样，只是引入的对象不同。

  1. main.js 中初始化:

    javascript
    import globalObserver from './qiankun/GlobalStateObserver';

export async function mount(props) {
  if (props.onGlobalStateChange) {
    globalObserver.init(props);
  }
  render(props);
}

  2. 组件中使用:

    vue
    <script setup>
import { onMounted, onUnmounted } from 'vue';
import globalObserver from '@/qiankun/GlobalStateObserver';

const handleRefresh = (payload) => { /* ... */ };
onMounted(() => globalObserver.on('REFRESH_UPLOAD', handleRefresh));
onUnmounted(() => globalObserver.off('REFRESH_UPLOAD', handleRefresh));
</script>

其他方案探讨：原生API ​

我们也可以使用浏览器原生 API 进行通信，但各有优劣。

BroadcastChannel ​

BroadcastChannel API 允许同源的不同浏览器上下文（窗口、iframe等）进行广播通信。

  • 优点: API 简单，天生支持一对多广播。
  • 缺点: 有同源限制。如果主子应用部署在不同源（如 localhost:8080 和 localhost:8081），此方案将失效。

window.postMessage ​

postMessage API 允许跨源窗口安全通信。

  • 优点: 支持跨域，非常灵活。
  • 缺点: API 复杂，是点对点通信。要实现一对多，仍然需要在子应用内部配合事件总线来分发消息，这绕了一圈又回到了原点，并且破坏了 qiankun 的封装，不推荐在 qiankun 架构中直接使用它进行主子通信。

总结与方案对比 ​

特性Qiankun setGlobalState + Event BusBroadcastChannelpostMessage
通信模式发布/订阅广播点对点
跨域支持支持 (框架封装)不支持 (同源)支持
实现复杂度低非常低高
与Qiankun集成官方推荐，无缝可用，但受限繁琐，不推荐
解决多处监听优雅解决原生解决需配合事件总线

最终建议 ​

  1. 首选方案：Qiankun setGlobalState + 应用内事件总线。这是最符合 qiankun 设计思想、最稳健、最解耦的方案，是微前端通信的“最佳实践”。
  2. 备选方案：如果能确保所有应用同源，且只需要简单的消息通知，BroadcastChannel 是一个轻量的选择。
  3. 避免使用：尽量不要在 qiankun 中直接使用 postMessage 来替代框架的通信机制，这会增加不必要的复杂性和维护成本。

Vite+Vue+UnoCSS 在 Qiankun 微前端中的样式冲突终极解决方案 ​

深度剖析了在 Vite + Vue3 + UnoCSS 技术栈下，结合 Qiankun 微前端框架时遇到的样式冲突及 HMR 失效等疑难杂症，并提供了一套可用于生产环境的终极解决方案。

问题背景 ​

当我们在 Qiankun 微前端架构中，主应用和子应用都采用 Vite 和 UnoCSS 时，会遇到一个非常诡异的问题：当子应用加载后，主应用的 UnoCSS 样式会失效，或者子应用的样式会直接覆盖主应用的样式。更有甚者，HMR（热更新）会变得不可预测或完全失效。

很多人会疑惑：Qiankun 不是号称有 JS 沙箱和 CSS 沙箱吗？为什么样式隔离不起作用？

通过深入分析，我们发现这背后隐藏着两个性质完全不同、但又相互交织的冲突。

两大核心冲突：揭示问题的本质 ​

冲突一：CSS 内容冲突 (运行时表现) ​

这是最表层、最容易理解的冲突。

  • 表现：后加载的应用样式覆盖先加载的应用样式。
  • 根源：Qiankun 默认的 CSS 沙箱（experimentalStyleIsolation: false）只负责在子应用卸载时移除其添加的 <style> 和 <link> 标签。在运行时，所有应用的样式表都存在于主应用的 <head> 中，共享同一个全局作用域。
  • 陷阱：即使您不写任何自定义规则，UnoCSS 默认注入的 preflights (CSS Reset 样式) 也会导致冲突。例如，子应用的 button { ... } 规则会覆盖主应用的 button 规则，导致主应用按钮样式异常。
  • 结论：只要多个应用都使用 UnoCSS，CSS 内容冲突就必然发生。

冲突二：JS 引擎 / HMR 冲突 (开发时表现) ​

这是更深层、导致开发体验崩溃的根本原因。

  • 表现：主应用的 UnoCSS HMR 失效，不再对 class 变化做出反应；或者子应用间切换导致 HMR 失效，必须刷新浏览器。
  • 根源：开发模式下，每个 Vite 应用都会启动一个独立的 Dev Server，并在浏览器端注入一个 HMR 客户端脚本 (/@vite/client)。当 Qiankun 将一个子应用加载到主应用中时，相当于在同一个页面里，同时运行了两个活跃的 HMR 客户端实例。
  • 源码分析：这两个 HMR 客户端会争抢 window 上的全局句柄 (如 window.__VITE_HMR_CLIENT__)、重复注册全局事件监听、建立各自独立的 WebSocket 连接。后启动的子应用 HMR 客户端会严重干扰甚至“踢掉”先启动的主应用 HMR 客户端的通信链路，导致其“失聪”。
  • 结论：@unocss/vite 插件由于强依赖健康的 HMR 通信，成为了这个底层冲突最显著的“受害者”。这才是导致开发时主应用 UnoCSS “哑火”的元凶。

INFO

  1. 实际项目中更多出现的是冲突二，使用unocss预设已经能满足几乎大部分业务场景，排除自定义规则。
  2. 要解决冲突一也简单，官方预设配置前缀 prefix，但是模板种书写类需要手动加前缀，体验不是很好；或者借助插件 postcss-prefix-selector 自动将所有类名转换加前缀，唯一注意的一点的在 plugins 中注意引入顺序(插件执行顺序由下至上，可以放在顶层最后执行)

Monorepo 挑战：共享库的设计模式 ​

在 Monorepo 架构下，我们通常会有一个共享组件库 (shared-ui)。如何处理它的 UnoCSS 依赖，也是一个关键问题。

模式一：宿主提供能力 (Headless UI) ​
  • 做法：共享库本身不含 uno.config.ts，它只在 peerDependencies 中声明需要 unocss。由最终消费它的宿主应用（主应用或子应用）在其 uno.config.ts 中配置 content.filesystem 去扫描共享库的源码，并为其生成样式。
  • 优点：共享库与构建工具解耦，非常纯粹。
  • 缺点：强依赖宿主的正确配置。
模式二：自包含能力 (Self-Contained) ​
  • 做法：共享库拥有自己的构建流程和 vite.config.ts。通过在 uno.config.ts 中使用 safelist，精确地将自己组件用到的样式（例如仅图标）打包到独立的 CSS 文件中。
  • 优点：完全解耦，可移植性强，不依赖任何宿主。
  • 缺点：需要手动维护 safelist，增加了共享库自身的构建复杂度。

WARNING

但是，仍避免不了底层核心的问题，JS 引擎 / HMR 冲突，以上2种模式一样是不生效的

终极解决方案(目前为止) ​

清晰地分离开发环境和生产环境的策略是解决所有问题的关键。

开发环境：追求最佳 HMR 体验 ​

为了解决致命的“JS 引擎冲突”，推荐采用 “Vite 插件 + PostCSS 插件混合模式”。

核心思想：让主应用继续使用功能强大的 @unocss/vite 插件，而让所有子应用降级使用更纯粹、无 HMR 冲突的 @unocss/postcss 插件(或者反过来)。

1. 主应用配置 ​

  • package.json: 依赖 @unocss/vite。

  • vite.config.ts:

    ts
    import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import unocss from 'unocss/vite' // 主应用使用 Vite 插件
import postcssPrefixSelector from 'postcss-prefix-selector'

export default defineConfig({
  plugins: [vue(), unocss()],
  css: {
    postcss: {
      plugins: [
        // 为主应用添加作用域，防止被 preflights 污染
        postcssPrefixSelector({
          prefix: 'body[data-app="main"]',
          // ...健壮的 transform 函数...
        }),
      ],
    },
  },
})

  • main.ts: 必须使用动态创建 Wrapper 的模式挂载，确保 prefix 能生效(postcss-prefix-selector的前缀)。

    ts
    // 动态创建 Wrapper 的挂载逻辑
let wrapper: HTMLDivElement | null = null;
function render(props: any) {
  const { container } = props;
  wrapper = document.createElement('div');
  wrapper.id = 'sub-app-1-wrapper'; // ID 必须和 prefix 匹配
  container.appendChild(wrapper);
  // ... createApp().mount(wrapper) ...
}

  • uno.config.ts: 配置 content.filesystem 扫描自己和需要用到的共享库。

  • main.ts: 入口文件配置 import 'virtual:uno.css'

2. 子应用配置（所有子应用均需如此） ​

  • package.json: 依赖 @unocss/postcss（注意：不是 @unocss/vite）。

  • vite.config.ts:

    ts
    import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import postcssPrefixSelector from 'postcss-prefix-selector'

export default defineConfig({
  plugins: [vue()], // 这里没有 unocss() 插件！
  css: {
    postcss: {
      plugins: [
        // 步骤1：让 unocss 作为 postcss 插件工作
        unocssPostcss(), 
        // 步骤2：紧接着，用 prefix 插件给刚生成的 CSS 加上作用域
        postcssPrefixSelector({
          prefix: '#sub-app-1-wrapper', // 每个子应用使用唯一前缀
          // ...健壮的 transform 函数...
        }),
      ],
    },
  },
})

  • main.ts: 必须使用动态创建 Wrapper 的模式挂载，确保 prefix 能生效(postcss-prefix-selector的前缀)。

    ts
    // 动态创建 Wrapper 的挂载逻辑
let wrapper: HTMLDivElement | null = null;
function render(props: any) {
  const { container } = props;
  wrapper = document.createElement('div');
  wrapper.id = 'sub-app-1-wrapper'; // ID 必须和 prefix 匹配
  container.appendChild(wrapper);
  // ... createApp().mount(wrapper) ...
}

  • postcss.config.mjs:

    ts
    import UnoCSS from '@unocss/postcss'

export default {
  plugins: [
    UnoCSS(),
  ],
}

  • uno.config.ts: 正常配置，扫描自己和共享库。

    ts
    import { defineConfig, presetWind3 } from 'unocss'

export default defineConfig({
  content: {
    filesystem: [
      '**/*.{html,js,ts,jsx,tsx,vue,svelte,astro}',
    ],
  },
  presets: [
    presetWind3(),
  ],
})

  • style.css:

    css
    @unocss preflights;
@unocss default;

/*
  Fallback layer. It's always recommended to include.
  Only unused layers will be injected here.
*/
@unocss;

生产环境：追求绝对隔离 ​

在 build 模式下，JS 引擎冲突完全不存在。我们唯一需要关心的就是 CSS 内容冲突。
