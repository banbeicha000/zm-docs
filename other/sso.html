请求头配置 ​

✅ 标准但常用于业务控制的请求头 ​

这些虽然是标准的，但被大量用于自定义逻辑：

请求头用途
Authorization用于携带 token（如 Bearer token、JWT 等）进行身份验证
Content-Type指定请求体格式，如 application/json、multipart/form-data
Accept指定客户端接受的响应类型，如 application/json，后端可根据此返回对应格式
Origin指定请求来源，用于 CORS 判断
Referer指定请求来源 URL，安全审计、防盗链等用到
User-Agent指定客户端信息，可用于设备判断或接口分流（如 PC / 移动）
Accept-Language指定语言偏好，常用于国际化返回（如 zh-CN、en-US）

🔧 非标准但常用于业务场景的请求头（自定义） ​

这些是非标准（non-standard），需要客户端和后端约定好。大多以 X- 或直接业务前缀命名：

请求头常见值用途说明
X-Requested-WithXMLHttpRequest标识为 Ajax 请求，防止返回重定向
X-Auth-TokenJWT / Token身份认证用，替代 Authorization（更灵活）
X-Session-IdUUID标识用户 Session ID，微服务下传递登录态
X-Tenant-Id企业 ID多租户系统中区分租户
X-Trace-IdUUID链路追踪 ID，日志和 APM 系统中常用
X-Client-Version1.0.2前端应用版本号，用于灰度、兼容性控制
X-Platformweb / ios / android标识客户端平台，适配不同返回逻辑
X-TimezoneAsia/Shanghai客户端时区，辅助时间显示
X-Envdev / prod区分环境，用于接口代理或调试辅助

🛡️ 注意点

  • 非标准头建议以 X- 开头，避免与标准头冲突。
  • 现代一些建议移除 X- 前缀，直接使用自定义名称，比如：Tenant-Id、Trace-Id，但必须后端允许。
  • 浏览器有些头是受保护的（forbidden headers），不能直接修改，例如 Host、User-Agent，除非使用某些特殊方式（如代理中间层）。

📌 示例：Axios 中设置常用头部

ts
axios.get('/api/user', {
  headers: {
    'Authorization': `Bearer ${token}`,
    'X-Requested-With': 'XMLHttpRequest',
    'X-Tenant-Id': 'tenant-123',
    'X-Trace-Id': uuid(),
    'X-Client-Version': '1.2.3',
    'X-Platform': 'web'
  }
});

🔍 X-Requested-With: XMLHttpRequest 是什么？ ​

这是一个非标准请求头，由许多 JavaScript 库（如 jQuery）默认发送，常用于告诉后端该请求是通过 Ajax 发出的，而不是浏览器直接访问页面发出的。 ✅ 它的用途和作用：

  1. 💡 后端判断请求来源

后端可以通过这个头来判断请求是否来自异步请求，从而决定返回方式： ​

  • 如果是普通页面请求：返回重定向（302）

  • 如果是 Ajax 请求：返回 JSON 错误（如 401、200）

  1. 🚫 阻止浏览器自动跳转

虽然这个头本身不会阻止 302 行为，但后端可以根据它避免返回 302 重定向，从而间接让前端避免跳转。 ​

前端如何处理认证失败（401）时，能否获取后端返回的响应内容 ​

📦 假设后端返回：

http
HTTP/1.1 401 Unauthorized
Content-Type: application/json

{
  "code": 401,[sso.md](../../../../WeChat%20Files/wxid_6s0vitp90u6922/FileStorage/File/2025-07/sso.md)
  "message": "请先登录"
}

⚠️ 但注意以下几种会拿不到响应内容的情况：

❌ 情况一：后端返回 401，但没有响应体 ​

http
HTTP/1.1 401 Unauthorized
Content-Length: 0

➡️ error.response.data 是空的

❌ 情况二：浏览器拦截跨域请求的响应体（CORS 没配好） ​

如果接口是跨域的，后端返回了 401，但 没有设置 Access-Control-Allow-Origin，或没有包含 Access-Control-Allow-Credentials，浏览器出于安全策略：

拦截了响应，Axios 拿不到 response 对象，只能拿到 error.message 或 undefined。

✅ 后端需要确保跨域时正确返回 CORS 头： ​

http
Access-Control-Allow-Origin: https://your-frontend.com
Access-Control-Allow-Credentials: true

# 深入解析一种经典的后端驱动SSO认证流程

在现代前端项目中，接入公司的统一认证平台（UAP/SSO）是一个常见需求。本文将详细记录并分析一种非常经典且优雅的认证方案：它完全由后端驱动，前端应用对认证过程几乎无感知，实现了业务逻辑与认证逻辑的完美解耦。

## 场景设定

首先，我们明确一下故事中的几个主角：

-   **前端应用 (FE):** `http://project.example.com`
    -   一个现代单页面应用（SPA），使用 `axios` 进行网络请求。
    -   在请求头中会携带 `X-Requested-With: XMLHttpRequest`。
-   **项目后台 (BE):** `http://api.project.example.com`
    -   为前端提供数据接口的服务。
    -   与前端应用属于**同主域** (`.example.com`)，这是实现无缝 Cookie 共享的关键。
-   **统一认证平台 (UAP):** `http://sso.example-auth.com`
    -   负责处理用户登录、验证凭据、生成票据（Ticket）的独立服务。
    -   与我们的项目**跨域**。

> **注意：** 以上所有服务均使用 `http` 协议，这构成了我们后续讨论安全问题时的核心。

## 核心流程详解

整个认证流程如同一场精心编排的“重定向之舞”，前端应用在此过程中非常“被动”，只需静静等待最终的结果即可。

### 流程图解

使用 Mermaid 序列图可以清晰地展示各个角色之间的交互：

```mermaid
sequenceDiagram
    participant Browser as 浏览器
    participant FE as 前端应用 (project.example.com)
    participant BE as 项目后台 (api.project.example.com)
    participant UAP as 统一认证平台 (sso.example-auth.com)

    Note over Browser, UAP: 初始状态：用户未登录
    Browser->>FE: 1. 访问受保护页面
    activate FE
    FE->>BE: 2. 发起API请求 (e.g., /user/info)
    deactivate FE
    activate BE

    BE-->>BE: 3. 检查无会话Cookie，判断未登录
    BE-->>Browser: 4. 返回 302 重定向至UAP<br/>Location: sso.example.com?service=api.../callback
    deactivate BE

    Browser->>UAP: 5. 遵循302，请求UAP登录页
    activate UAP
    Note over Browser, UAP: 用户在UAP输入用户名密码
    UAP-->>UAP: 6. 验证凭据，生成一次性Ticket
    UAP-->>Browser: 7. 返回 302 重定向至后台回调接口<br/>Location: api.../callback?ticket=...
    deactivate UAP

    Browser->>BE: 8. 遵循302，请求后台回调接口(携带Ticket)
    activate BE
    BE->>UAP: 9. [服务端] 验证Ticket有效性
    activate UAP
    UAP-->>BE: 10. Ticket有效，返回用户信息
    deactivate UAP
    BE-->>BE: 11. 创建本地会话，生成session_id
    BE-->>Browser: 12. 返回 302 重定向至前端页面<br/>Header: Set-Cookie: session_id=...<br/>Location: project.example.com/dashboard
    deactivate BE

    Browser->>FE: 13. 遵循302，访问前端目标页 (此时已携带Cookie)
    activate FE
    FE->>BE: 14. 再次发起API请求 (自动携带Cookie)
    deactivate FE
    activate BE
    BE-->>BE: 15. 验证Cookie有效
    BE-->>FE: 16. 返回 200 OK 和业务数据
    deactivate BE

分步解析 ​

  1. 访问受保护资源 用户打开前端应用的一个需要登录的页面（如 /dashboard）。前端应用加载后，立即向后端 api.project.example.com/user/info 发起数据请求。

  2. 后端拦截并重定向 后端收到请求，通过检查请求头中是否包含有效的会话 Cookie（例如 session_id）来判断用户是否登录。发现未登录，后端不返回 401 错误，而是直接返回一个 HTTP 302 Found 响应。

    http
    HTTP/1.1 302 Found
Location: http://sso.example-auth.com/login?service=http://api.project.example.com/auth/sso-callback
    • Location 指向 UAP 的登录页。
    • service 参数是关键，它告诉 UAP 认证成功后应该将用户带回哪里。注意，这里设置的是后端的回调接口，而不是前端页面。

  3. 用户在 UAP 登录 浏览器接收到 302 响应后，会立即中断当前的 AJAX 请求，并将整个页面跳转到 UAP。用户在此页面完成登录操作。

  4. UAP 颁发 Ticket 并重定向回后端 UAP 验证用户成功后，会生成一个一次性、短时效的 ticket，然后再次发起 302 重定向，将浏览器导向第 2 步中 service 参数指定的地址。

    http
    HTTP/1.1 302 Found
Location: http://api.project.example.com/auth/sso-callback?ticket=ST-123456-abcdefg

  5. 后端验证 Ticket，创建会话并设置 Cookie 浏览器现在请求了我们的后端回调接口，并附上了 ticket。后端执行以下关键操作：

    • 获取 Ticket：从 URL 参数中解析出 ticket。
    • 验证 Ticket：向 UAP 发起一个服务端到服务端的请求，验证该 ticket 是否有效。这是为了防止伪造 Ticket。
    • 创建会话：UAP 确认 ticket 有效后，后端为该用户创建自己的会话（Session），并生成一个唯一的 session_id。
    • 最终重定向：后端再次返回一个 HTTP 302 响应，这次它将把用户带回真正的前端页面。
    http
    HTTP/1.1 302 Found
Location: http://project.example.com/dashboard
Set-Cookie: session_id=xyz-abc-123; Path=/; Domain=.example.com; HttpOnly

    这个响应是整个流程的点睛之笔：

    • Location：指示浏览器跳转回最初想访问的前端页面。
    • Set-Cookie：在重定向前，将后端的会话凭证 session_id 写入浏览器。由于 Domain=.example.com 的设置，这个 Cookie 对 project.example.com 和 api.project.example.com 均有效。

  6. 登录成功，一切恢复正常 浏览器存储好 Cookie，然后跳转到前端页面。页面加载后再次发起 API 请求，此时请求头会自动携带上 session_id Cookie。后端验证此 Cookie 有效，返回 200 OK 和业务数据，流程闭环。

关键技术点分析 ​

后端驱动的优势 ​

这种模式最大的优点是前端逻辑极简。前端开发者无需关心任何认证细节（如何跳转、如何处理 Ticket），认证逻辑对前端是完全透明的。所有复杂的认证、会话管理都集中在后端，权责分明，易于维护。

X-Requested-With: XMLHttpRequest 的角色 ​

这个请求头是 axios 等库在发送 AJAX 请求时默认添加的，用于标识这是一个异步请求。在我们的场景中，后端选择对所有未登录请求都返回 302。但在其他架构中，后端可以利用此头进行区分：

  • 普通页面请求（无此头）：返回 302。
  • AJAX 请求（有此头）：返回 401 Unauthorized 和一个包含登录地址的 JSON 体，由前端的 axios 拦截器捕获并处理跳转。

显然，当前方案选择了更简单直接的“一视同仁”策略。

重大安全风险与改进建议 ​

当前流程在逻辑上是完美的，但在实现上存在致命的安全漏洞。

1. HTTP 明文传输：头号风险！ ​

致命风险

整个流程（UAP登录、Ticket传输、Cookie设置与传输）都发生在 HTTP 上。这意味着所有数据都是明文的。任何网络中间人（如不安全的公共 Wi-Fi）都可以轻易嗅探到：

  • 用户的登录密码。
  • URL 中的 ticket。
  • 响应头中的 session_id Cookie。

攻击者一旦窃取 session_id，就可以完美冒充用户，进行会话劫持。

解决方案：必须、一定、务必为所有服务（FE、BE、UAP）启用 HTTPS！ 这是现代 Web 应用的基石，可以加密所有通信，从根本上解决窃听问题。

2. Cookie 安全属性缺失 ​

后端的 Set-Cookie 响应头需要更加健壮，以抵御常见的 Web 攻击。

  • HttpOnly：强烈建议开启。它能防止客户端 JavaScript 读取 Cookie，有效防御 XSS 攻击窃取会话。
  • Secure：必须在启用 HTTPS 后添加。它确保 Cookie 只通过加密的 HTTPS 连接传输，防止在混合内容（HTTP/HTTPS）的网站中泄露。
  • SameSite：用于防御 CSRF 攻击。
    • SameSite=Lax (推荐)：在跨站导航（如点击链接）时允许发送 Cookie，但在跨站的 POST 请求或 iframe 中则会禁止。对于此场景是很好的平衡。
    • SameSite=Strict：最严格，完全禁止任何跨站情况下的 Cookie 发送。

一个更安全的 Set-Cookie 头应该像这样：

http
Set-Cookie: session_id=...; Path=/; Domain=.example.com; HttpOnly; Secure; SameSite=Lax

总结 ​

我们分析的后端驱动SSO认证流程是一个非常成熟、可靠的架构设计。它将认证的复杂性从前端剥离，实现了清晰的职责分离。

  • 优点：前端无感、逻辑集中、流程清晰。
  • 核心：巧妙利用 302 重定向和同域 Set-Cookie 完成认证闭环。

然而，其安全性完全依赖于底层的通信协议和正确的配置。安全永远是第一位的，请立即将您的项目迁移到全站 HTTPS！

常见问题： ​

1.为什么在无痕模式下看不到 302？ ​

这是一个非常敏锐的观察。有时在测试时，我们可能会发现，虽然认证流程（跳转到登录页再跳回）正常工作，但在 Chrome DevTools 的 Network 面板中（即使勾选了 Preserve log），我们却看不到预期的 302 状态码。

最核心的原因是：统一认证平台（UAP）上已经存在一个有效的登录会话了。

无痕模式（Incognito Mode）只保证在窗口关闭时清除所有数据，但在窗口的生命周期内，它和普通浏览器窗口一样会保持会话和 Cookie。

“快速通道”认证流程 ​

如果你的浏览器在 UAP 的域 (sso.example-auth.com) 下已经有了会话 Cookie（例如，在同一个无痕窗口中登录过其他系统），那么认证流程会走一条“快速通道”：

  1. 你的项目后台依然返回第一个 302，将你导向 UAP。
  2. 浏览器请求 UAP 时，自动带上了 UAP 的会话 Cookie。
  3. UAP 服务器识别出你已登录，于是跳过了登录页面。
  4. UAP 立即生成 ticket 并返回第二个 302，将你导向项目的后端回调接口。
  5. 后续流程照常进行。

整个过程（项目 -> UAP -> 项目）因为没有人工输入环节，发生得极快，可能在几百毫秒内完成。在 Network 面板中，这个快速的重定向链可能看起来像是一次简单的页面刷新，中间的 302 请求很容易被忽略或被浏览器内部缓存优化掉。

如何强制看到完整的 302 链？ ​

如果你想进行干净的调试，确保看到每一步，请按以下步骤操作：

  1. 打开一个全新的无痕窗口，不要复用旧的。
  2. 手动清除 UAP 会话：
    • 方法一：直接访问 UAP 的地址并点击“退出登录”。
    • 方法二：在 DevTools 的 Application > Cookies 面板中，找到 sso.example-auth.com 域，右键点击并选择 Clear。
  3. 确保 Network 面板的 Preserve log 已勾选。
  4. 再次访问你的项目地址。

完成以上步骤后，由于 UAP 中已无会话，它将被迫展示登录页面，你就能在 Network 面板中清晰地捕获到每一个 302 重定向请求了。

2.为什么拿到了cookie仍会重定向到认证平台，然后免登录直接刷新回当前页面 ​

问题场景分解 ​

  1. 首次访问/Session过期: 用户访问你的前端应用（比如 app.com）。
  2. 重定向到认证中心: 前端应用发现用户未登录，将页面重定向到统一认证平台（比如 sso.com）。
  3. 用户登录: 用户在 sso.com 输入账号密码成功登录。
  4. 重定向回应用: 认证平台 sso.com 将用户重定向回你的前端应用 app.com，并在 URL 中通常会携带一个 ticket 或 code。
  5. 前端获取凭证:
    • 前端拿到 ticket 后，调用后端接口（比如 /api/login）换取真正的会话凭证（Session/Cookie 或 JWT Token）。
    • 后端验证 ticket 成功，在响应头中通过 Set-Cookie 指令，在浏览器中种下一个用于身份认证的 Cookie（比如 SESSIONID），这个 Cookie 的域（Domain）通常是你的后端 API 所在的域。
  6. 正常使用: 用户在应用内操作，所有对后端 API 的请求，浏览器都会自动带上这个 SESSIONID Cookie。后端通过验证这个 Cookie 来确认用户身份，接口正常返回数据。
  7. 问题触发点: 用户执行某个特定操作，触发了一个特殊的 API 请求。
  8. 请求失败: 这个特殊的 API 请求没有携带 SESSIONID Cookie。
  9. 后端鉴权失败并重定向: 后端 API 的鉴权中间件发现这个请求没有有效凭证，认为用户未登录。根据 SSO（单点登录）的逻辑，它不会直接返回 401 Unauthorized，而是返回一个 302 Found 重定向响应，目标地址是当初配置的认证平台登录页 sso.com。
  10. “无感”的二次认证:
    • 浏览器收到 302 响应，自动跳转到 sso.com。
    • 由于用户刚才已经在 sso.com 登录过了，并且 sso.com 自身的会话仍然有效，所以认证平台根本不需要用户再次输入密码。它直接验证通过，并立即生成一个新的 ticket，再次重定向回你的前端应用 app.com。
  11. 页面刷新: 浏览器最终被重定向回 app.com，并且 URL 上带着新的 ticket。这在用户看来，就是当前页面突然被刷新了一下。刷新后，流程回到第 5 步，重新建立了会话，后续操作又恢复正常，直到再次触发那个有问题的 API 请求。

核心原因分析：为什么那个接口没带 Cookie？ ​

整个问题的根源在于第 8 步。一个正常运行的应用中，突然有一个请求不带 Cookie，这通常不是偶然的。以下是几个最常见的原因，你需要逐一排查：

1. API 请求的跨域（Cross-Origin）配置问题 (最常见) ​

这是最可能的原因。如果你的前端和后端 API 不在同一个源（协议、域名、端口号有一个不同），那么这就是跨域请求。

  • 问题: 对于跨域请求，浏览器默认是不会发送 Cookie 的。
  • 解决方案: 你需要在发起请求时，明确告知浏览器需要携带凭证。
    • 如果使用 axios: 需要在 axios 实例或单次请求中设置 withCredentials: true。
      javascript
      // 全局配置
axios.defaults.withCredentials = true;

// 或者单次请求配置
axios.get('https://api.example.com/special-data', {
  withCredentials: true
});
    • 如果使用原生 fetch: 需要在 fetch 的 options 对象中设置 credentials: 'include'。
      javascript
      fetch('https://api.example.com/special-data', {
  credentials: 'include' // 或 'same-origin'
});
  • 排查方向: 检查那个出问题的 API 请求代码，是不是它没有配置 withCredentials 或 credentials，而其他正常的请求都配置了？也许是你项目里封装了多个请求方法，而这个操作恰好调用了一个未正确封装的。

2. Cookie 的作用域（Domain 和 Path）不匹配 ​

Cookie 本身是有作用域的。如果请求的 URL 不在 Cookie 的作用域内，浏览器也不会发送它。

  • 问题:
    • Domain: 后端设置的 Cookie 可能指定了 Domain=.api.com，但那个有问题的请求发往了 special.api.com 或者一个完全不同的域名。
    • Path: Cookie 可能指定了 Path=/api，但那个有问题的请求发往了 /other-api/data。
  • 排查方向:
    1. 打开浏览器开发者工具 (F12)。
    2. 切换到 "Application" (或 "存储") -> "Cookies"。
    3. 找到你的会话 Cookie（比如 SESSIONID），查看它的 Domain 和 Path 字段。
    4. 切换到 "Network" (或 "网络") 面板，找到那个失败的请求，查看它的 Request URL。
    5. 对比请求的 URL 和 Cookie 的 Domain、Path 是否匹配。

3. 请求的 URL 协议（HTTP vs HTTPS）不匹配 ​

如果 Cookie 被设置了 Secure 属性，那么它只能通过 HTTPS 协议发送。

  • 问题: 你的网站是 https://app.com，后端 API 也都是 https://api.com，但那个出问题的 API 请求被错误地配置成了 http://api.com/special-data。
  • 排查方向: 在 "Network" 面板中检查失败请求的 URL，确认其协议是 https。

4. 特殊的请求方式或第三方库 ​

  • 问题: 这个请求可能不是由你常用的 axios 实例发起的。例如，它可能是一个文件上传组件、一个图表库或者其他第三方 JS 库内部发起的请求。这些库可能有自己的网络请求配置，并且默认不携带 Cookie。
  • 排查方向: 确定是哪个组件或哪段代码触发了这个 API 调用。如果是第三方库，查阅其文档，看如何配置请求以携带凭证。
实际项目中出现第2中情况 ​
  1. 初始状态: 用户登录后，可能最先与 /zk-admin-management 或 /zk-knowledge-qa-search 服务交互。这些服务在返回响应时，通过 Set-Cookie 指令种下了会话 Cookie。
  2. Path 的默认行为: 如果后端在设置 Cookie 时没有显式指定 Path 属性，浏览器或服务器框架会默认使用当前请求的 URL 路径作为 Cookie 的 Path。
    • 例如，如果设置 Cookie 的请求是 POST /zk-admin-management/login，那么 Cookie 的 Path 就会被默认设置为 /zk-admin-management。
  3. 问题触发: 当你的前端应用需要调用一个新服务下的接口，比如 /zk-document-processing/api/some-action 时：
    • 浏览器检查本地的 Cookie。它发现只有 Path 为 /zk-admin-management 和 /zk-knowledge-qa-search 的 Cookie。
    • 由于请求的路径 /zk-document-processing/... 与现有 Cookie 的 Path 都不匹配，浏览器不会在这次请求中携带任何一个会话 Cookie。
  4. 重定向循环: 后端的 /zk-document-processing 服务收到了一个没有 Cookie 的请求，认为用户未登录，于是触发了重定向到 SSO 的流程，这就解释了你看到的现象。
  5. “再次操作后才会有这个Path”: 这个重定向循环走完一遍后，最终会有一个请求（可能是认证回调请求）被 /zk-document-processing 服务处理，并成功设置了一个新的、Path 为 /zk-document-processing 的 Cookie。此时，你再操作调用这个服务下的接口就正常了，因为现在有匹配的 Cookie 了。

根源 ​

问题的根源在于：后端各个服务在设置身份认证 Cookie 时，没有统一 Path 属性，导致 Cookie 变成了“服务专属”的，无法在所有服务间共享。

解决方案 ​

这是一个典型的后端配置问题。前端虽然有“绕过”的办法，但既不优雅也不治本。最佳实践是在后端进行修复。

最佳解决方案：后端统一设置 Cookie 的 Path 为根路径 / (推荐) ​

这是最正确、最一劳永逸的解决方案。

你需要联系后端开发人员，让他们在所有设置会话 Cookie 的地方（登录接口、SSO回调处理接口等），显式地将 Cookie 的 Path 属性设置为根路径 /。

一个 Path=/ 的 Cookie 意味着，浏览器会向该域名下的所有路径发送这个 Cookie，无论请求的是 /zk-admin-management、/zk-knowledge-qa-search 还是 /zk-document-processing。

优点:

  • 一处修改，永久解决。
  • 前端代码无需任何改动。
  • 符合微服务或多模块应用下共享会话的标准实践。
  • 系统逻辑更清晰、更健壮。

备选方案：前端在调用前“预热”会话 (不推荐) ​

如果后端由于某些原因（比如历史包袱、权限问题）暂时无法修改，前端可以采用一种“hack”的方式来规避。

思路: 在第一次调用 /zk-document-processing 下的任何业务接口之前，先主动向该服务路径下发送一个“无害”的初始化请求（比如 GET /zk-document-processing/api/health 或专门的 /zk-document-processing/api/init-session 接口）。

这个请求会因为没有 Cookie 而触发 SSO 重定向，并最终带回一个 Path 为 /zk-document-processing 的新 Cookie。等这个“预热”流程完成后，再执行真正的业务接口调用。

缺点:

  • 治标不治本: 只是一个创可贴，未来新增 /zk-new-service 路径时，问题会再次出现。
  • 增加复杂性: 前端需要维护一个状态，来判断哪些服务的会话已经被“预热”。
  • 性能损耗: 增加了额外的网络请求和一次不必要的重定向，用户在首次操作时会感到明显的延迟或页面闪烁。
  • 体验差: 逻辑上非常奇怪，难以维护。
